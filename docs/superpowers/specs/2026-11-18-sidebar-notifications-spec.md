# Selected-session notification flyout specification

**Design baseline** — `docs/superpowers/specs/2026-11-18-sidebar-notifications-design.md`, commit `12090ebd76e8862133b0d648ee63ced686e25852`, SHA-256 `94fa9dbf037ce2a9d2feaac1b3ca963632ff0920255f54f6df62270677a7ed3b`. The approved comparison selects desktop layout A.

**Scope** — Implement the browser presentation and its selected-session projection. The session daemon remains authoritative and retains its existing in-memory lifecycle, wire format, APIs, limits, and legacy compatibility. This specification supplies implementation and acceptance contracts. Task decomposition and scheduling belong to the implementation planner.

## Existing boundaries and ownership

The existing `SessionNotificationController` owns the browser's single selected-inbox projection. Its inputs already arrive through `prepareSelectedSession`, `clearSelectedSession`, `refreshSelectedSession`, `applyInboxEvent`, and environment synchronization. `SessionController` calls the bridge during selection and connects the selected session's socket. Retain these integration points and the controller's responsibility for target, generation, snapshot, event and mutation ordering. Extend its observable operation state and announcement delivery as needed for this contract. A view must never initiate an inbox request on its own.

`PiWebUiApp` owns the open surface, presentation mode, focus intent, modal isolation, and association with the selected session. `ActivityRail` receives the bell's presentation state and callbacks. The compact rail launcher receives the same count and availability information. A focused tray component receives the presentation projection and action callbacks. It renders the same list in either layout and owns no API client, socket, persistence, or independent inbox cache. The app owns one permanently mounted announcement host outside the tray and chat. The existing polite and assertive regions form one announcer.

The `SessionNotificationTarget` identity is `{ machineId: string; sessionId: string; cwd: string }`. Equality requires all three fields. A notification or mutation additionally belongs to a `daemonInstanceId`. The selected-session generation changes on every selection preparation or clear, including a same-key reselection. App surface and focus-intent generations are separate from controller selection and request generations. They are ephemeral and do not persist across reloads.

Existing shared types in `src/shared/apiTypes.ts` are authoritative. A snapshot contains `daemonInstanceId`, `catalogRevision`, `summary`, `notifications`, and `dismissThrough`. `summary` carries `sessionId`, `cwd`, `inboxRevision`, `retainedCount`, `discardedCount`, and optional `highestSeverity`. Each notification carries `id`, `order`, `receivedAt`, `severity`, `message`, and `truncated`. `dismissThrough` is `{ order: number; overflowWatermark: number }`. Inbox events contain the same identity and summary, plus `added`, `dismissed`, `cleared`, or `resync` delta. The daemon retains at most `SESSION_NOTIFICATION_LIMIT` (100) visible rows and truncates messages at `SESSION_NOTIFICATION_MESSAGE_BYTES` (8 KiB). These values describe existing behavior and are not new client-configurable limits.

The existing client methods form the wire boundary. `SessionLookup` is `SessionRef | string`, and `machineId` is optional in these existing methods.

```ts
notificationInbox(session: SessionLookup, machineId?: string): Promise<SessionNotificationInboxSnapshot>
dismissNotification(session: SessionLookup, daemonInstanceId: string, notificationId: string, machineId?: string): Promise<SessionNotificationInboxSnapshot>
dismissAllNotifications(session: SessionLookup, daemonInstanceId: string, through: SessionNotificationDismissThrough, machineId?: string): Promise<SessionNotificationInboxSnapshot>
```

They route through the existing client API and parsers. Preserve their machine and `cwd` routing, dynamic-segment encoding, and current server endpoints. The feature introduces no server, daemon, WebSocket protocol, plugin, browser storage, global inbox, unread synchronization, or retained notification history.

## Presentation projection and request admission

Derive a single presentation from current app selection, machine status and runtime negotiation, the controller's accepted-support evidence and selected inbox, plus actual current operation state. The fresh-only `selectedNotificationView()` supplies the `fresh` branch. The following TypeScript describes the required inputs and view boundary. Equivalent internal names are permitted, but all variants and inputs must be distinguishable and observable by the app.

```ts
type NotificationCapability = "unknown" | "supported" | "unsupported";
type NotificationOperation = "idle" | "checking-health" | "checking-capability" | "loading-inbox";

interface NotificationPresentationInputs {
  selectedSession: SessionInfo | undefined;
  selectedMachine: Machine | undefined;
  machineHealth: MachineHealth | undefined;
  machineRuntime: MachineRuntime | undefined;
  acceptedSupport: { runtimeGeneration: number; daemonInstanceId?: string } | undefined;
  runtimeGeneration: number;
  selectionGeneration: number;
  inbox: SelectedSessionNotificationInbox | undefined;
  operation: { target: SessionNotificationTarget; selectionGeneration: number; kind: Exclude<NotificationOperation, "idle"> } | undefined;
}

type NotificationPresentation =
  | { kind: "ineligible" }
  | { kind: "offline"; target: SessionNotificationTarget; operation: NotificationOperation }
  | { kind: "capability-unavailable"; target: SessionNotificationTarget; operation: NotificationOperation }
  | { kind: "unsupported"; target: SessionNotificationTarget }
  | { kind: "loading"; target: SessionNotificationTarget; operation: NotificationOperation }
  | { kind: "unavailable"; target: SessionNotificationTarget; operation: NotificationOperation }
  | { kind: "fresh"; target: SessionNotificationTarget; view: SelectedSessionNotificationView; operation: NotificationOperation };

interface NotificationTrayInputs {
  presentation: NotificationPresentation;
  sessionTitle: string;
  mode: "flyout" | "sheet";
  onDismiss(notificationId: string): void;
  onDismissAll(): void;
  onRetry(): void;
  onClose(): void;
}
```

The app derives the inputs from current state and controller publications. A tray callback dispatches to the app/controller and never starts transport directly. Surface open state, focus intent, pending-mutation identity, and the live-announcement cursor are app/controller state outside the tray projection. An operation indicator is current only when its target and selection generation match the current selection. `runtimeGeneration` is an ephemeral per-machine client counter advanced on a confirmed runtime or daemon replacement and on machine removal. A successful capability refresh for the same observed runtime does not itself advance the counter. Accepted support is applicable only to its matching machine and generation.

A selected session is eligible when it is the current active selection, has a machine, nonempty session ID and cwd, and is neither archived nor a client-pending start. Use the existing pending-session predicate rather than inferring it from the display name. Any projection, request, result, operation indicator, or focus intent for another target is ineligible for publication. Selection rebind occurs synchronously at the selection boundary, before awaiting transcript or inbox work. No previous target's title, rows, count, dismissal state, or error may appear as the new selection's.

Apply the following precedence whenever selection, environment, operation, or inbox changes.

1. No eligible selection yields `ineligible`. Disable the bell, hide the badge, and close an open surface with the connected fallback described below.
2. An explicitly unreachable remote yields `offline`, including when it was offline before selection. Keep the bell enabled, show an offline explanation and Retry, and suppress numeric count, rows, and dismiss actions. Local and remote reachability follow the controller's existing machine-status rules. Unknown status is not itself an explicit offline result.
3. Capability is `supported` when the existing negotiated capability or accepted-support rule establishes support for the current machine/runtime. A successful inbox response or accepted valid inbox event supplies accepted-support evidence. Do not infer unsupported from an absent inbox. Missing or failed negotiation without applicable accepted evidence is `unknown` and yields `capability-unavailable`, with Retry. A successful current runtime negotiation that establishes no notification capability, without applicable accepted evidence, yields `unsupported`, with an explanation and no inbox retry. Invalidate accepted evidence when the machine is removed or its runtime/daemon is known to have been replaced, so an older runtime's evidence cannot authorize a request to its replacement. A transient failed negotiation by itself does not erase valid same-runtime accepted evidence.
4. With support and reachability established, a matching fresh inbox yields `fresh` even while its background refresh is pending. The row list and count are the effective optimistic view. A current request does not blank a still-current fresh view.
5. With no matching fresh inbox, show `loading` only while a current, admitted inbox request is actually pending. A health or capability retry may show its own checking state only during that real operation. A stale, missing, or nominally `loading` projection with no matching admitted request yields `unavailable`, with Retry. Failure ends checking/loading and exposes the resulting offline, capability-unavailable, unsupported, or unavailable state.

The bell and compact launcher show a badge only for `fresh`. A current total of zero has no visual badge. No other state communicates a numeric count, including zero. An enabled unavailable bell can be opened. A fresh zero inbox presents an explicit empty state. The open tray names the selected session using the existing session-title fallback and includes the full effective count only when fresh.

The controller and app recovery flow own request admission.

- Do not issue notification inbox or dismiss requests for an ineligible, explicitly unreachable, or unsupported target. Unknown capability requires runtime negotiation before an inbox request. Mutation admission has the stricter fresh-view rules below.
- For offline Retry, call the existing `MachineController.refreshMachineHealth(machineId)` recovery path. Re-evaluate the returned/current health. While it remains explicitly offline, end the operation in `offline` and issue no inbox request. If health permits, refresh runtime capability through `MachineController.refreshMachineRuntime(machineId)` and re-evaluate before an inbox refresh. A failed health check remains unavailable and must not be treated as successful recovery. Both methods return `undefined` on failure, and runtime refresh also returns `undefined` when superseded. Treat that result as an unsuccessful or superseded operation rather than as permission to advance.
- For unknown capability Retry, use the same runtime refresh path used by `PiWebUiApp.renegotiateUnreadMachine`, then re-evaluate current accepted/negotiated support. Start an inbox refresh only if supported and reachable. A failed or superseded negotiation ends in the observed state. For a supported stale/missing inbox Retry, call `SessionNotificationController.refreshSelectedSession` for the current target. Reconnect and an eligible environment transition use the existing session/controller recovery flow to refresh that same target.
- Capture target and selection generation at admission. Recheck after every awaited health, capability, or inbox operation. A late result cannot update the new selection's presentation, operation state, error, or focus. Machine-controller updates that legitimately belong to a machine remain machine-scoped and cannot authorize work for a superseded selected target.
- The existing health and runtime refresh methods publish their own state and global errors before their promises settle. Extend those paths with an optional ownership guard and caller-owned error reporting for notification recovery, preserving existing default behavior for other callers. Evaluate the guard before publishing either a machine result or an error. A superseded notification retry cannot publish an old health/runtime result or global error into the newer selection. Return an unsuccessful/superseded result to the recovery flow and surface a current failure in the tray. Preserve runtime's per-machine refresh ordering and ensure overlapping health recovery cannot overwrite a newer same-machine observation.
- Coalesce same-generation inbox refreshes. An explicit Retry joins a read that already covers the current request. Reserve at most one trailing refresh for a real invalidation of the in-flight read, such as a subscription gap or a reducer resync. Renders and tray visibility do not start requests. Offline and unsupported targets remain ineligible for inbox reads. Recovery is event-driven and bounded.

**Subscription coverage.** A selection-time inbox read can start while the session socket is connecting. `SessionSocket` signals raw WebSocket OPEN, while `sessionRoutes.ts` sends `session.subscribed` after attaching the socket to the event hub. The event hub does not replay updates written before attachment. Raw OPEN alone neither starts a second inbox read nor reserves a trailing read. Observe the existing `session.subscribed` marker for the current socket incarnation even during the transcript join, using the socket's identity guard. On the first marker for that incarnation, ensure one inbox read admitted after the marker, reusing any matching post-marker read already admitted. If a pre-marker read is pending, queue the catch-up as its one trailing read. If the pre-marker read has settled, start the catch-up directly. A delayed response to a pre-marker request does not establish post-marker coverage. Apply the same coverage rule on reconnect. Duplicate markers and overlapping requests for the same coverage join that work. Any catch-up still requires current selection, reachable machine, and established notification support. This uses the existing subscription event and leaves the transcript and extension-entry refresh behavior intact.

For a refresh, capture the target, selection generation, current socket incarnation and daemon observation. Buffer or otherwise order incoming events at the existing join seam. A same-daemon snapshot may replace the authoritative base only when its inbox revision is at least the current base revision. Reconcile ordered valid events and coalesce catch-up work for a gap, `resync`, inconsistent summary, or a join that cannot be safely reconciled. A failed refresh makes a no-longer-current inbox unavailable and leaves a still-current fresh inbox visible only if its identity, reachability, capability, and freshness remain valid.

A daemon ID is an opaque identity. When a valid current-socket event or current request observes replacement, retire the previous daemon identity for that selection, clear its optimistic operations and announcement delivery identity, mark the projection stale, and obtain a current snapshot. Invalidate requests begun before the replacement observation. A retired socket, a retired daemon's late event or response, a prior selection generation, and an older refresh completion cannot reinstate the retired identity, overwrite new rows, clear current pending state, or announce. A response bearing a different daemon from a request that was current when it began is replacement evidence only if no newer daemon observation or request has superseded it. Use socket/operation generations as well as daemon IDs because IDs have no comparison order. Invalidate support evidence from the old runtime first, then allow a valid event or inbox response from the replacement to establish support for its own daemon. If fresh support cannot be established, use the capability recovery flow before requesting the replacement snapshot. Reconnect to the same daemon retains the announcement delivery cursor and reconciles snapshots without replay. A genuine replacement starts a new delivery identity and re-establishes the snapshot baseline.

## Bell, tray, and content

At `ACTIVITY_RAIL_DESKTOP_MEDIA_QUERY`, currently `(min-width: 1181px)`, render the bell in the fixed control group immediately above Settings. When the existing installed-app reload control is visible, place it above the bell. Reload remains fixed and outside `REORDERABLE_IDS`. The bell is also fixed and excluded from drag/drop and plugin order. Retain the reload control in its existing supported layouts. The new ordering supersedes the current description in `docs/navigation-panel.md` that places reload immediately above Settings.

The full effective count is `retainedCount + discardedCount`, using the controller's existing selected-view overlay semantics. Render `1` through `99` as their full decimal values and every value above 99 as `99+`. The bell accessible name and the compact launcher accessible name expose the uncapped current count and selected-session context. For a zero fresh count, the accessible name still communicates zero even though the badge is hidden. For an unavailable count, the accessible name communicates availability without presenting a number. The bell reports expanded state and references its controlled surface with a valid ID relationship in the rendered accessibility tree. `ActivityRail` and `PiWebUiApp` use separate Lit shadow roots, so a plain string ID reference to an element in a different root is insufficient. Arrange a same-scope target or a browser-supported element reference that resolves across the actual roots, and verify the relationship in the real browser accessibility tree. The compact launcher and sheet require the same effective relationship.

On desktop, the bell toggles one non-modal, labelled region adjacent to the rail. It overlays available navigation space, retains the chat's existing size, does not dim or isolate the background, and scrolls its list and long messages without clipping controls. The surface has a selected-session heading, a close control, notification rows, an overflow indication, and Clear all when appropriate. Each row exposes severity, readable received time, message, the existing truncation notice when `truncated`, and the existing descriptive dismiss label. Preserve `notificationInboxOverflowLabel`, `notificationMessageTruncationLabel`, and equivalent existing accessible wording. Escape and close control close it. Pointer activation outside the bell and tray closes it without cancelling the pointer event or stealing the destination's focus. Use the composed event path so shadow DOM children count as inside. Selecting another session by outside pointer action closes the flyout. A keyboard or route selection change that leaves it open immediately displays the new target's applicable state.

Below 1181px, the bell remains in the compact rail. Activating it closes that rail and opens a viewport-filling modal sheet with the same presentation and actions. While the compact rail is closed, its launcher exposes the same fresh badge and full accessible count. The sheet respects viewport bounds, safe-area insets, and scrolling. It is a labelled modal dialog with a programmatically focusable heading, a close control, and real focus and background isolation. Render exactly one visible notification list during and after a layout transition.

Remove the notification inbox, collapse state/control, and its live regions from `ChatView` and the above-chat notices. Keep unrelated session warnings, speech errors, action-blocking errors, and legacy command output in their existing contexts. Capable-runtime filtering of legacy notification-tagged command output continues through `shouldFilterLegacyNotification`. Incapable runtimes retain their legacy output. Opening, closing, switching layout, and switching selection never themselves dismiss an inbox.

## Interaction, modal isolation, and focus

A keyboard or assistive-technology activation of the desktop bell opens the region and moves focus to its heading. A pointer activation opens it without moving focus away from the bell or pointer destination. Compact opening always focuses the sheet heading after the rail has closed and the sheet is connected. New notifications never open a surface or move focus. A close via Escape, the close control, or the bell restores focus to the visible launcher for the current layout, provided no newer focus intent or modal has superseded that restoration. Outside pointer close does not restore focus. Opening another application modal closes the desktop flyout without restoring focus over the new modal.

The sheet's Tab and Shift+Tab cycle through connected, enabled controls inside it. With no other enabled controls they return to the heading. Covered application content must be inert to pointer and keyboard interaction, and excluded from sequential focus and the active accessibility tree while the sheet is open. Restore the prior isolation state on close, selection ineligibility, resize to desktop, and component disposal. A backdrop may close the sheet only if its handler preserves the same restoration and isolation contracts. Do not rely solely on `aria-modal` or a bubbling child key handler.

`PiWebUiApp.onKeyDown` is registered on `window` in capture phase and currently checks prompt-editor speech before its other modal guards. When the compact sheet is open, handle Escape at that capture boundary before speech cancellation or any background action, prevent and stop the event, close the sheet, and restore focus. Suppress other covered-app global shortcuts at that boundary while permitting the sheet's own Tab, Shift+Tab, and controls to receive their events. Desktop Escape closes the open flyout before background Escape actions. When focus is in the desktop flyout, avoid dispatching app shortcuts from its controls. When focus is in the uncovered desktop background, preserve normal non-modal chat and application shortcuts. Existing modal and compact-rail guards retain their behavior when the notification surface is closed.

An open surface survives crossing the 1181px breakpoint without changing target, dismissing, or replaying announcements. On desktop-to-compact, close any compact rail, establish isolation, then focus the equivalent connected tray control if focus was inside the desktop tray, or the sheet heading otherwise. On compact-to-desktop, remove isolation and, if focus was inside the sheet, focus its equivalent connected desktop tray control, falling back to the heading. The equivalence key includes control role and, for a row, notification ID. A control that is missing, disabled, or disconnected cannot be focused. Do not leave focus on a hidden desktop bell or a removed compact element. Subsequent close returns to the desktop bell or the compact rail launcher according to the current layout. If the preferred launcher is disabled, missing, or disconnected, use a connected, visible application focus fallback. Do not reopen the compact rail merely to restore focus.

For a focused row's optimistic removal, use the pre-removal visible order to choose the next remaining row's dismiss control, then the previous row's control, then the tray heading. Clear all targets the heading. The tray stays open and shows its empty state after the last row disappears. If a selection or availability change removes the focused control while the surface stays open, focus its heading. If it closes due to ineligibility, use the visible launcher or connected application fallback.

Deferred focus work captures target, surface generation, the intended destination and a focus-intent token. Before focusing after render, recheck that all are current, the surface is still open in the applicable layout, and the user has not moved focus or initiated another pointer/keyboard action. Close, selection change, another modal, resize handoff, and later user focus intent invalidate obsolete work. An asynchronous mutation success or rollback must never pull focus back from the composer or another surface.

## Dismissal, overlays, and counts

The controller is the sole mutation owner. At admission capture `{ target, selectionGeneration, daemonInstanceId, operationId }` from the current matching fresh view and verify reachability and support again. Individual dismissal additionally captures a visible notification ID. Clear all additionally captures a copy of the authoritative current `dismissThrough` pair. Send that exact target, daemon and pair through the existing API. Keep the captured watermark fixed for the lifetime of the action. Multiple distinct individual dismissals can overlap. Clear all can start while individual requests are pending and immediately pauses admission of further dismissals until it settles. This includes individual dismissals of rows above its captured watermark. Keep those rows visible and counted, with their dismiss buttons disabled while Clear all is pending. A repeated activation of a pending row or Clear all issues no request. After Clear all succeeds or rolls back, re-enable individual dismissal for any still-visible, nonpending row in a current fresh inbox. Each admitted operation owns only its own overlay and completion.

Maintain the authoritative inbox separately from controller-owned optimistic overlays. An individual overlay hides its ID. A Clear all overlay hides rows whose `order` is at most the captured `order` and the discarded portion through the captured `overflowWatermark`. Compute remaining discarded count using the existing watermark semantics in `selectedNotificationView`, including its existing optimistic last-visible-row behavior. The badge, heading, overflow indication, and actions all consume that same effective view. A post-admission notification with greater order or newly discarded overflow beyond the captured watermark remains visible and counted. Neither an individual overlay nor a Clear all overlay removes an unrelated newer row.

Apply successful snapshots only after target, selection generation, operation identity, reachability, capability, daemon, and revision checks. A same-daemon older snapshot cannot overwrite a newer event or snapshot. Remove only the completing operation's overlay, preserving other operations' effects. If an accepted authoritative event already reflects a mutation before its response, its later completion must not reintroduce the removed row or erase newer state. A result for a previous selection or daemon cannot clear the new target's pending state, including when the same notification ID is reused. Pending registries and `finally` cleanup therefore require operation/generation ownership, not an ID-only unconditional deletion. If the same selection becomes offline or loses support while a mutation is pending, retire the completing operation's own overlay without publishing its snapshot or a stale success, mark the inbox stale, and reconcile on eligible recovery. A previous selection or daemon owns no cleanup in the new one.

The daemon returns its current snapshot without applying a dismissal when the request carries a different `daemonInstanceId`. Treat such a response from a still-current operation as replacement evidence, subject to the ordering checks above. Retire the old operation and overlay, reconcile the replacement snapshot or refresh it, and never infer that the requested dismissal took effect on the replacement daemon. If a newer observation already superseded the response, discard it. On a current operation failure, remove only its overlay, report the appropriate failure in the current UI, and reconcile via the existing selected-session refresh when eligible. The effective view immediately derives again from the latest authoritative base and remaining overlays. Thus an affected still-authoritative row reappears, but a row already removed by another successful operation or authoritative event stays removed. A transport failure may be ambiguous if the daemon applied the request before its response was lost. The subsequent snapshot decides the final state. A stale or offline view suppresses rows and count until refreshed. A failure or completion after supersession may not report an error, mutate state, or move focus in the new selection.

Keep daemon behavior for overflow, truncation, runtime close, archive, delete, replacement, and service disposal. Do not invent a durable history or manufacture previously discarded rows. Existing session switching does not clear either session's daemon-owned inbox.

## Live announcement contract

Mount one app-owned announcer for the life of the app, independently of chat, tray, responsive layout, and fresh-only selection. Keep stable polite and assertive live-region elements and the existing severity-only labels from `notificationAnnouncementLabel`. Error severity uses the existing assertive channel, and info/warning use the existing polite channel. Append a bounded recent set of keyed announcement nodes, with a maximum of `SESSION_NOTIFICATION_LIMIT`, without recreating earlier nodes when the tray opens, closes, resizes, or the inbox temporarily becomes stale. Do not include message contents in the announcement label.

For the active selection, track delivery by target plus daemon ID, actual notification ID, and monotonic notification `order`. Track the highest delivered/established order and recent delivered IDs separately from the fresh view and snapshot contents. Only a validated, accepted `added` live event for the current selected identity and daemon may append. An event with an already delivered ID or order at or below the cursor cannot append again, including if its inbox revision differs. Ordered join and event validation must still reject duplicates, stale events, gaps, mismatched identities, and inconsistent deltas. Snapshots reconcile the inbox and never append announcement nodes.

On initial selection or daemon replacement, establish the baseline from the accepted snapshot's existing retained rows and `dismissThrough.order`. Existing baseline rows produce no announcement. An initial join event already covered by that baseline is reconciliation, while a validated subsequent live addition beyond it may be announced. For a same-daemon refresh with an established pre-refresh baseline, retain and validate live additions received during the join against the ordered event stream. An addition accepted after that baseline is announced once even if the eventual snapshot also contains it. If a gap or inconsistent event prevents acceptance, reconcile by snapshot without treating snapshot rows as live events. Refresh, stale-to-fresh recovery, and same-daemon reconnect never reset the established delivery cursor or reinsert prior announcement nodes. Selection change and confirmed daemon replacement retire the old identity and start a new baseline. Events from a previous socket, target, or daemon are ignored. This is bounded, in-memory delivery bookkeeping rather than notification persistence.

## Verification contract

Use `.agents/skills/testing-guide/SKILL.md` for all test work and `.agents/skills/code-quality-architecture/SKILL.md` for production changes. Tests exercise public controller entry points and rendered behavior, not only private helper return values. Use controlled deferred promises and explicit event barriers rather than sleeps for races. Add focused tests only where an existing test would miss the required regression.

### Deterministic fixtures

Use two machines, `local` and `remote`, and targets A `{machineId: "local", cwd: "/a", sessionId: "s"}`, B `{machineId: "remote", cwd: "/b", sessionId: "s"}`, and C `{machineId: "local", cwd: "/other", sessionId: "s"}`. Shared session IDs make machine and cwd checks observable. Supply independently resolvable health, runtime, inbox and mutation promises, with call records including target, daemon and watermarks. Drive actual app/controller selection, environment synchronization, retry, event and mutation entry points. Use daemon `d1` and replacement `d2`, monotonic inbox revisions, globally ordered notification IDs, valid summary counts and dismiss-through values, and a socket-incarnation token. For overflow, start with 100 retained rows plus 3 discarded, a captured overflow watermark of 8, then append a new row and advance the watermark to 9. For announcements, record appended node identities and live-region DOM node identity across state changes. Browser fixtures use the app's real responsive CSS and native event/focus handling with controllable API/socket data, not jsdom geometry.

### Focused Vitest acceptance cases

- **V1 — placement and counts.** Render desktop and compact rail with no eligible session, fresh totals 0, 1, 99, 100 and 103, and each unavailable state. Assert enabled/disabled control, uncapped accessible count, visual `99+`, zero badge suppression, valid expanded/control relationships, title fallback, fixed placement directly above Settings, and stable reorder/plugin behavior. With PWA reload enabled assert reload, bell, Settings order.
- **V2 — one inbox and preserved notices.** Open each layout and inspect one list with severity, time, truncation, overflow and labelled actions. Confirm the old chat inbox, collapse control and competing chat live regions are absent while unrelated warnings, speech/action errors, and legacy output remain. An empty fresh inbox stays open and shows its explicit empty state.
- **V3 — state precedence and no-request paths.** Table-drive ineligible/pending/archived, initially offline remote with absent inbox, unknown and failed capability, confirmed unsupported, supported fresh, real pending refresh, and stale/missing with no request. Assert exact visible state, badge and actions. Assert zero inbox requests in offline, unknown before negotiation, unsupported, and on repeated renders/open/close. A still-fresh background refresh retains its rows and count.
- **V4 — recovery.** Hold and resolve health and runtime promises separately. Retry offline while health remains offline and assert no inbox call. Change health to online, resolve capability supported, then observe exactly one inbox call. Unknown capability must resolve before inbox admission. Failed health, failed negotiation, unsupported capability, and failed inbox refresh leave a non-loading explanatory state. Same-daemon accepted support survives a transient negotiation failure, and runtime replacement invalidates old evidence. Assert legacy tagged output remains on incapable runtime and filtering remains on capable runtime.
- **V5 — target and operation supersession.** Start A's health, capability, inbox and selected-session work, select B or C, then resolve A in each order. Assert B/C's title, status, count, rows, pending indicator and errors remain theirs, including equal session IDs. Exercise the real machine-controller recovery boundary so an old health/runtime rejection cannot publish a global error or overwrite a newer same-machine observation. Deliver old-socket events and old mutation results. Change an eligible selection through keyboard/route while open and assert immediate rebinding without previous data. Ineligible selection closes the surface. Through the real session selection and notification refresh entry points, hold a selection-time read, emit raw initial OPEN, then settle the read before emitting the subscription marker. Assert exactly one inbox request through settlement. Deliver `session.subscribed` and assert exactly one catch-up whose snapshot includes a notification written after the first snapshot and before subscription. Repeat with the marker arriving while the pre-marker request is held, including a duplicate marker, and verify a single trailing catch-up. A read admitted after the marker satisfies that incarnation's coverage without an extra read. Repeated invalidations during one deferred refresh cause at most one trailing request.
- **V6 — optimistic action ownership.** Dismiss a focused row, assert immediate effective count/list and captured API identity, then reject and assert rollback/error for still-authoritative data. Dismiss two different rows concurrently, complete in both orders, and make one fail.
