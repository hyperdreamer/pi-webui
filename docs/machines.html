PI WEBUI fleet

Connect trusted PI WEBUI runtimes when one machine is not enough.

Most PI WEBUI setups only need one runtime. When you do have more than one, machine federation lets the PI WEBUI instance you opened act as a gateway to other trusted runtimes while each machine keeps its own repositories, credentials, sessions, Pi package settings, and plugins.

What Fleet does

A machine is a PI WEBUI runtime endpoint. The local machine is synthesized automatically. Remote machines are opt-in PI WEBUI runtimes that you register with a base URL and, optionally, a bearer token.

After registration, the browser keeps talking to the current PI WEBUI origin. The gateway contacts the selected remote PI WEBUI server and routes that machine's projects, workspaces, sessions, files, git state, activity, terminals, and Pi package-management operations to the browser UI.

Fleet shape 
Browser
  ↓
PI WEBUI gateway you opened
  ├─ [ Local runtime ]
  │
  ├─ [ Remote PI WEBUI runtime A ]
  │     ↓ selected machine
  │     projects, workspaces, sessions, terminals, Pi packages, plugins
  │
  └─ [ Remote PI WEBUI runtime B ]

When to use it

Federation is useful when you have more than one place where agents should work, but you want one stable browser entrypoint.

▦

Many dev boxes

Register a workstation, home server, cloud VM, or client-specific host without moving repositories.

⇄

One gateway

Open one trusted PI WEBUI URL and switch machines instead of juggling browser tabs and tunnels.

⌁

Local ownership

Each target machine keeps its own Pi auth, sessions, worktrees, terminal state, Pi package settings, and plugins.

Set up another runtime

Install and run PI WEBUI on every machine you want to register. The remote URL must be reachable from the gateway server, not just from your browser.

Install on each target 
$ npm install -g @hyperdreamer/pi-webui --allow-scripts=node-pty
$ pi-webui install
$ pi-webui doctor

Prefer a private path such as NetBird, Tailscale, WireGuard, private LAN, SSH tunnel, or an authenticated reverse proxy. If the remote is behind a path prefix, include that prefix in the machine URL, for example https://devbox.example.test/pi-webui. The machine registry normalizes the trailing slash; when opening that deployment directly in a browser, use its canonical https://devbox.example.test/pi-webui/ URL and configure the proxy to redirect the slashless form.

Do not expose PI WEBUI directly to the public internet. Register machines only over trusted network paths and only when you trust the endpoint.

Add a machine

  1. Open the PI WEBUI instance you want to use as the gateway.
  2. Open Actions → Add Machine.
  3. Enter the remote PI WEBUI base URL, including http:// or https://.
  4. Accept the suggested name or enter a friendlier sidebar label.
  5. Paste an optional bearer token if the remote endpoint requires one.

The Machines section appears when there is more than one machine. Select a machine, then add projects, workspaces, and sessions on that selected machine.

Removing a remote machine only removes it from this gateway's registry. It does not stop the remote PI WEBUI service or delete projects, workspaces, sessions, or credentials on the target machine.

What works remotely

After you select a machine, the rest of the app works in that machine's scope. The gateway routes the selected-machine work to the target PI WEBUI runtime.

  • Projects and workspaces.
  • Files, previews, git status, and diffs.
  • Pi sessions, transcripts, prompts, model controls, and commands.
  • Activity indicators and realtime updates.
  • Terminals and terminal command runs.
  • Pi package listing, install, remove, and update from Settings → Pi packages when supported by the target PI WEBUI runtime.
  • Remote plugins from the selected machine.

Slow or distant machines

Every remote machine has its own request patience: how long the gateway waits for that machine to start answering one proxied request before it gives up. Raise it for a host behind a slow VPN or on a cold disk; lower it when you would rather see a failure sooner.

Patience belongs to the gateway's copy of the machine record, not to the remote machine's own config. Set it in the machine dialog: open the ⋯ actions menu for the machine, either in the Machine switcher or in the Machines section, choose Edit, and change Request timeout. Actions → Add Machine asks for the same value on a new machine, and a failing session-list notice can open the same dialog for you.

  • Default: 120 seconds (120000 ms). A record that stores no value behaves exactly like one that stores the default, and a new machine starts at 120.
  • Range: 5 to 180 seconds (5000–180000 ms). The field takes seconds with up to millisecond precision, such as 5.001; a value outside the range is rejected and stays in the field for correction instead of being rounded or clamped.
  • Precedence: a route with its own budget keeps it. Health and runtime probes stay at 3 seconds, the remote plugin manifest stays at 10 seconds, and the skills, Pi package, and session-tree operations keep their 5-minute budget. Everything else the gateway proxies uses the machine value.
  • When it applies: the next request after you save. No session, session-daemon, or gateway restart is needed, and a request already in flight keeps the patience it started with.

The budget covers the wait for the remote's response headers, not the response body. Once headers arrive the transfer has no timer, so a large transcript or file keeps streaming after the deadline has passed.

Background refreshes the UI starts by itself — activity, git status, memory and learned-skills catalogs, and automatic list reconciliation — give up after 20 seconds regardless of the stored patience, so a slow machine cannot hold a hidden refresh open indefinitely. Work you trigger, such as selecting a machine, project, workspace, or session, keeps the machine patience.

What a slow session list shows

A remote session list still waiting after five seconds explains the wait in the Sessions section: Loading sessions from Dev Box… 0:42 of 2:00. The first value is the elapsed wait, the second is the machine's patience, and both use whole m:ss values; the wait counts up every second. When the remote starts answering, the line changes to Receiving sessions from Dev Box… while the body arrives.

A timed-out or interrupted read stays visible as a typed failure that names the machine and the elapsed wait, and a timed-out read also names the budget it exceeded — for example Dev Box didn't answer within 2:00. Waited 2:03., or Dev Box stopped responding while sending sessions. Waited 2:00. when the wait succeeded but the transfer did not. Two actions follow it:

  • Try again re-reads only that workspace's session list. The open session, its transcript, and its stream stay as they are.
  • Raise limit opens that machine's edit dialog with the patience field focused, so you can accept a longer wait and save.

What patience cannot fix

A longer budget helps a slow machine, not one that is unreachable, unauthenticated, or already cut off by an earlier hop.
  • A reverse proxy in front of the gateway, or between the gateway and the remote, can cut the connection well before the machine budget. Raising the machine value past your proxy timeouts will not make that request succeed.
  • Federation does not bypass another hop's ceiling. When the gateway reaches a machine through an older PI WEBUI gateway, that gateway's own patience and defaults still bound the request.
  • Giving up in the browser only ends the wait. A session-list enumeration that the remote's session daemon already started keeps running and finishes that pass on its own.

Credentials stay on the target machine

Model-provider credentials, Pi configuration, Pi package-manager settings, OAuth state, repositories, and active session runtimes stay on the selected target machine. The gateway does not copy them into its own Pi configuration.

  • API-key provider configuration can be proxied through the gateway.
  • OAuth login should be completed by opening the remote PI WEBUI directly.
  • The optional machine bearer token is stored by the gateway and sent to the remote while proxying requests.

Use Actions → Open Selected Machine PI WEBUI when you need to authenticate directly on a remote machine or inspect it outside the gateway.

Plugins follow the selected machine

When you select a remote machine, PI WEBUI tries to load that machine's discovered plugins through the gateway. Remote plugin actions, workspace panels, and workspace labels only appear while that machine is selected, and documented file and terminal helpers run against that machine.

Remote plugins are still trusted browser-side code. Only federate machines whose PI WEBUI plugins you are comfortable loading in the browser.

Trust boundaries

Machine federation is for trusted users, trusted PI WEBUI servers, and trusted network paths. Adding a machine gives the gateway permission to contact that URL and forward user-initiated PI WEBUI traffic to it.

  • Use private networking, an SSH tunnel, or an authenticated reverse proxy.
  • Do not include credentials in the machine URL itself.
  • Use bearer tokens or proxy authentication when a remote endpoint needs an extra gate.

Troubleshooting

Remote machine records are stored on the gateway in ~/.pi-webui/machines.json. If PI_WEBUI_DATA_DIR is set, they live under $PI_WEBUI_DATA_DIR/machines.json.

  • Use Actions → Refresh Selected Machine to re-check health.
  • Make sure the remote URL is reachable from the gateway server.
  • Open the remote PI WEBUI directly to verify it is running and to complete provider login flows.
  • For a machine that is simply slow, raise its Request timeout only as far as your proxy path allows, then use Try again.
  • Check gateway logs with pi-webui logs for proxy timeouts or upstream errors.
