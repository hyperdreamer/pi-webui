What platforms are supported?

PI WEBUI can run anywhere its runtime dependencies work. The automatic pi-webui install command uses a supported per-user service manager when one is available.

  • User-service install: use npm install -g @hyperdreamer/pi-webui --allow-scripts=node-pty and pi-webui install.
  • WSL: if your distro has systemd enabled, the installer may work; otherwise use the manual run path.
  • Native Windows: outside WSL is not the recommended path today.

Is PI WEBUI a Pi web UI?

Yes. PI WEBUI is a web UI for Pi Coding Agent that runs and supervises persistent sessions from a browser. Unlike simple session viewers, PI WEBUI is built around real server-side workspaces, long-running session daemons, git worktrees, remote machines, terminals, files, and multi-device supervision.

How does the embedded Browser work?

On desktop, select the globe Browser icon in the Activity Rail. The panel has tabs, an address bar, reload control, page-zoom controls, a draggable title bar, and a lower-right resize handle. Use + to open a tab and its × control to close it. Tabs last while the panel is open; page zoom is remembered in this browser.

Browser is a lightweight embedded viewer, not a native browser or a server-side proxy. The panel labels this mode explicitly. It accepts http:// and https:// addresses and renders them in a sandboxed, no-referrer frame. Pages whose X-Frame-Options or Content-Security-Policy: frame-ancestors policy disallows framing can refuse to load, and an HTTPS PI WEBUI deployment may have its browser block an HTTP page as mixed content.

Remote browser mode is unavailable in this installation by design. PI WEBUI does not start a remote Chromium runtime or browserd, and it provides no remote browser controls or pixel stream. There is no remote site-login session or PI WEBUI-managed destination-cookie storage. The iframe remains subject to the normal cookie policy of the user's browser; PI WEBUI does not proxy, inspect, or rewrite those cookies.

No setting rewrites page headers or turns this viewer into a proxy. A future remote-browser mode would require an authenticated principal, an isolated sandboxed browser runtime with a private control channel, and enforced public-web egress. Those security prerequisites are not deployed or configurable today, so use a normal browser for sites that block framing or require local-browser capabilities.

The address field tracks pages opened from the Browser controls. For privacy and browser security, PI WEBUI cannot inspect a different-origin page, so following links within an external page may not update the displayed address. Use the address field or a new tab to navigate directly when needed.

Tools are failing, node is not found, or Pi cannot find commands

The shell environment needs to be set up so login shells have the required PATH entries for PI WEBUI, Pi, and any tools your agents need. PI WEBUI services run commands through a non-interactive login shell owned by systemd or launchd, so an interactive terminal—or even a caller-invoked login shell—can work while the native service fails.

Run diagnostics 
$ pi-webui doctor
  • bash: put PATH setup in ~/.bash_profile or ~/.profile. If ~/.bash_profile exists, source ~/.profile from it if needed.
  • zsh: put PATH setup in ~/.zprofile, not only ~/.zshrc.
  • fish: prefer universal PATH setup, for example fish_add_path -U ....

Avoid relying only on prompt hooks, shell integrations that rewrite PATH while rendering a prompt, or interactive-only shell files for tools needed by services. Version-manager shims are usually the most reliable option for service environments.

What does pi-webui doctor check?

It keeps two kinds of checks separate. General login-shell readiness covers Node 22.19.0 or newer, npm, Pi, and optional ripgrep. Native-service diagnostics validate only the exact prerequisites of the selected service plan in the real systemd user-manager or launchd gui/<uid> context. Development installs follow their installed checkout plan; production checks are clearly labelled prospective when the installed executable strategy cannot be reconstructed safely.

Missing plan requirements fail doctor and include login-file guidance. Manager, timeout, malformed-output, and cleanup failures are reported as probe infrastructure problems rather than being mislabeled as PATH drift. On unsupported/manual-only platforms, native-service drift checks are skipped. Doctor also checks that the node-pty native module can load, prints installed and running PI WEBUI versions, and reports systemd lingering when relevant.

I installed Node with nvm, fnm, asdf, or another version manager

Version managers often initialize in interactive shells only. Some tools, including fnm and mise when used through shell activation instead of shims, depend on shell hooks or prompt-time PATH updates that are unreliable in non-interactive login shells.

  • Prefer version-manager shims when available; for mise, use shims or enable its shim setup rather than relying only on shell activation.
  • Move any required version-manager initialization to your login shell file.
  • Make sure node --version is at least v22.19.0 from bash -lc, zsh -lc, or your detected shell.
  • Run pi-webui doctor again after changing shell files.

pi-webui-sessiond cannot load pty.node

npm 12 blocks dependency installation scripts unless they are explicitly approved. If PI WEBUI was installed without approving node-pty, its required native module can be missing even though npm reported a successful installation.

Reinstall PI WEBUI with approval limited to node-pty:

Allow the node-pty installation scripts 
$ npm install -g @hyperdreamer/pi-webui --allow-scripts=node-pty

Then run pi-webui install again, or restart pi-webui-sessiond if you run PI WEBUI manually. The flag does not enable installation scripts for other dependencies.

User service manager is unavailable

The automatic installer needs a supported per-user service manager. On WSL without systemd, containers without a user service manager, or minimal environments, run the two processes manually:

Manual run 
$ pi-webui-sessiond
# in another terminal
$ PI_WEBUI_PORT=8808 pi-webui-server

I cannot open the web UI

  • Check pi-webui status.
  • Check logs with pi-webui logs.
  • Make sure port 8808 is not already in use.
  • On a remote server, use an SSH tunnel: ssh -L 8808:127.0.0.1:8808 user@server.

Can I expose PI WEBUI to the public internet?

Do not expose it directly to the public internet. PI WEBUI assumes trusted users and trusted server paths. For remote access, bind only to an interface that is already private and controlled: for example the server's VPN IP, a private LAN IP, or localhost behind an SSH tunnel.

When you connect over a VPN, 127.0.0.1 usually means your own device, not the server, so the server must listen on its VPN/private-network address or sit behind a tunnel/proxy.

Avoid 0.0.0.0 unless a firewall, VPN, or reverse proxy strictly limits who can reach the port.

How do I connect another PI WEBUI machine?

Install and run PI WEBUI on the target machine, make its PI WEBUI URL reachable from the gateway through a trusted path, then open the gateway and choose Actions → Add Machine. The browser keeps talking to the gateway while projects, sessions, files, and terminals run on the selected remote runtime.

  • Use NetBird, Tailscale, WireGuard, private LAN, SSH tunnel, or an authenticated reverse proxy.
  • Remote Pi auth, OAuth state, sessions, terminals, repositories, and plugins stay on the target machine.
  • API-key provider configuration can be proxied, but OAuth login should be completed by opening the remote PI WEBUI directly.
  • Remote plugins are trusted browser code and only appear while that machine is selected.
  • If the remote reports offline, check that the gateway server can reach the remote URL and try Actions → Refresh Selected Machine.

Should I run PI WEBUI on my laptop or a server?

You can run it locally, but PI WEBUI is most useful on a machine that stays on. A remote dev box, home server, cloud VM, or workstation gives agents a stable place to keep working while your laptop becomes just a client.

Local development can become a blocker when one device owns the tools, secrets, shells, editor, and agent runtime. Remote AI-driven development unlocks persistent work: agents keep running, sessions remain available, and you connect from whatever screen you have.

Can I use local plugins with production PI WEBUI?

Yes. Put trusted browser-side plugins in ~/.pi-webui/plugins/<plugin-id>/, or symlink a development folder there. Reload the browser tab after edits. If PI_WEBUI_DATA_DIR is set, use $PI_WEBUI_DATA_DIR/plugins instead.

Sessions stop unexpectedly

Active agent runtimes are owned by the session daemon. Browser disconnects and web/API restarts should not stop them. If they stop anyway, check whether the session daemon service restarted or crashed.

Session daemon logs 
$ pi-webui status
$ pi-webui logs

Where are logs?

Use the service log command:

Logs 
$ pi-webui logs
